# RE:SAFE — AI Digital Safety & Recovery Platform

딥페이크·불법촬영물·온라인 사기 등 디지털 범죄 피해자가 **신고 → 상담 → 삭제요청 → 후속지원**을 한 흐름으로 진행할 수 있도록 돕는 플랫폼입니다. 이 저장소는 해커톤 MVP 코드베이스이며, VS Code에서 바로 열어 개발을 이어갈 수 있는 Next.js/TypeScript/Supabase 구조입니다.

> ⚠️ **이 코드는 데모(SIMULATED) 단계입니다.** 실제 플랫폼 크롤링, 실제 LLM 연동, 실제 EEG 기기 연동은 구현되어 있지 않습니다. 아래 "실제 vs 시뮬레이션" 표에서 어떤 기능이 진짜 동작하고 어떤 기능이 자리만 잡아둔 것인지 확인하세요.


## 3. 4단계 흐름과 기능 명세

### Step 1. 신고 — 반복 설명 없이 안전하게 접수 (`components/Report.tsx`)
- **구현됨:** 경찰 사이버범죄 신고 매뉴얼(A~F 영역)에 대응하는 **12개 질문**을 순서대로, 대화형으로 진행합니다 (`lib/types.ts`의 `INTAKE_QUESTIONS`). 모든 질문에 "건너뛰기"가 있어 답하기 어려운 항목을 스킵할 수 있습니다.
- **구현됨:** 12개 답변이 모이면 `lib/ai/categorize.ts`가 **디지털 성범죄 / 사이버사기 / 사이버 명예훼손·모욕 / 기타 디지털 범죄** 중 하나로 분류하고, 분류별로 검증된 실제 연락처(112, 디지털성범죄피해자지원센터 02-735-8994, 여성긴급전화 1366, 경찰청 ECRM, 금융감독원 1332 등)를 제시합니다.
- **자리만 잡아둠(SIMULATED):** PDF 진술서 다운로드. 데모 HTML 버전(`resafe.html`)에는 `window.print()`를 이용한 PDF 저장이 구현되어 있습니다. Next.js 버전에서는 동일 로직(`buildStatementHTML()` + `window.print()`)을 `Report.tsx`의 버튼에 연결하면 됩니다 — 라이브러리 기반 PDF(jsPDF 등)가 아니라 브라우저 인쇄를 쓰는 이유는 한글 폰트 임베딩 문제를 피하기 위함입니다.
- **왜 이렇게 설계했나:** 피해자가 경찰서·상담센터·플랫폼마다 같은 이야기를 반복하는 것이 2차 피해입니다. 매뉴얼 순서 그대로 한 번만 답하게 하고, 그 결과를 구조화된 형태로 어디든 들고 갈 수 있게 하는 것이 핵심입니다.

### Step 2. 상담 — AI 상황 정리와 지원 안내 (`Report.tsx`의 "추가 상담" + `AiSecurityCard.tsx`)
- **구현됨:** 신고 플로우와 별도로, 자유 대화형 "추가 상담" 창(`chat2`)이 있습니다. 모든 입력은 `lib/ai/guard.ts`의 **AI 보안 레이어**를 통과합니다.
- **구현됨 — AI 보안 레이어 (`lib/ai/guard.ts`):**
  - `INJECTION_RULES` 10종: 시스템 프롬프트 탐색, 이전 지시 무시, 역할 변경(관리자 모드 등), 타 사용자 정보 조회 시도, 인코딩된 페이로드 등을 정규식으로 탐지.
  - `CRISIS_RULES`: 자살·자해 신호를 탐지하면 차단이 아니라 **상담 연계 메시지**(1393, 109)로 분기.
  - `stripHiddenInstructions()`: 증거 텍스트·외부 페이지 텍스트에서 숨은 지시 문장을 줄 단위로 제거 — AI에게 "원문"이 아니라 "정제된 텍스트"만 전달하기 위함.
  - 사이드바의 "AI 가드 켜짐/꺼짐" 토글로 방어 전/후 차이를 직접 시연할 수 있습니다.
- **왜 이렇게 설계했나(설계 전제):** 가해자가 피해자의 지인이거나 같은 서비스에 접근할 수 있다는 전제를 둡니다. "한 번만 말한다" 원칙 때문에 한 세션에 신고·증거·삭제요청·회복 기록이 모두 모이므로, AI 하나가 뚫리면 여러 민감정보가 한꺼번에 노출됩니다. 그래서 AI가 다루는 모든 입력(대화, 증거 파일, 외부 페이지)을 공격 경로로 보고 방어합니다.
- **자리만 잡아둠(SIMULATED), 다음 단계에서 할 일:**
  - 지금은 규칙 기반(정규식) 1차 필터만 구현되어 있습니다. 실제 LLM 연동 시 "규칙 기반 1차 필터 통과 → LLM 기반 2차 판정" 구조를 추가해야 합니다.
  - 세션 격리(조회 범위를 서버가 쿠키/세션으로 강제, LLM이 결정하지 못하게)는 아직 미구현 — `requireUser()`가 JWT로 사용자를 식별하지만, "이 케이스만 조회 가능"하도록 강제하는 것은 현재 RLS 정책에만 의존합니다.
  - 출력 가드(시스템 프롬프트 유출 방지용 카나리 토큰, 미동의 PII 노출 차단)는 아직 미구현.

### Step 3. 삭제요청 — 플랫폼·기관 연계 삭제 요청 (`components/TraceRemove.tsx`)
- **구현됨:** 추적 후보 목록(현재는 `lib/ai/provider.ts`의 `simulatedProvider`가 고정 데모 데이터 반환) → "삭제요청" 버튼 → 상태 추적(`prepared → submitted → reviewing → removed/rejected/unknown`)까지 전체 흐름이 동작합니다.
- **구현됨:** `lib/security/phash.ts`의 8×8 평균 해시 + Hamming distance로 "같은 이미지의 변형본"을 유사도(%)로 비교하는 로직 — 데모 HTML 버전에서는 실제 캔버스로 동작을 확인했습니다. Next.js 버전에도 동일 함수가 포팅되어 있으나, 실제 업로드→비교 UI 연결은 다음 단계 작업입니다.
- **시뮬레이션:** 실제 플랫폼 크롤링/스크래핑, 실제 삭제요청 API 연동은 없습니다. `TraceProvider` 인터페이스(`lib/ai/provider.ts`)로 추상화되어 있어, 실제 공급자를 붙일 때 이 인터페이스만 구현하면 됩니다 — 단, 반드시 **플랫폼 ToS/robots.txt 준수, 공개 데이터만 조회, 무단 접근·로그인 우회 금지** 원칙을 지켜야 합니다 (아래 "화이트 해킹 경계" 참조).

### Step 4. 후속지원 — 진행 상황 관리와 회복 연계 (`components/Recover.tsx`, `Prevent.tsx`, `Vault.tsx`)
- **구현됨:** 뉴로피드백 세션 기록 UI(데모 난수 데이터), 법률/심리 상담 연계 연락처, 예방 체크리스트.
- **구현됨 — 비가시 워터마크 (`lib/security/watermark.ts`):** PNG 이미지의 블루 채널 LSB에 "RSAF" + 16자리 코드를 심어, 언제·어디에·어떤 목적으로 게시할지(게시 예정일 포함)를 눈에 보이지 않게 기록합니다. 지인 범죄 억제 + 유출 시 후보 좁히기 목적. **한계(항상 고지할 것):** 무손실 PNG에서만 보존되며, JPEG 재압축·리사이즈·스크린샷에는 살아남지 않습니다. 100% 유출자 식별을 보장하지 않는 보조 수단입니다.
- **구현됨 — 증거 보관함 (`Vault.tsx`):** 이미지/영상은 SHA-256 해시만 계산해 저장(원본 비전송), 텍스트 증거는 "AI 요약"을 누르기 전까지 원문을 어디에도 저장하지 않습니다(브라우저 메모리 한정) — 피해자 본인이 "정리해서 넘길지"를 직접 결정하는 원칙.
- **시뮬레이션:** 실제 EEG 기기 SDK 연동, 딥페이크 생성 차단(얼굴 인식 기반) 기술은 미구현.

## 5. 다음 개발 중점: 화이트 해킹 & 보안 심화

> **경계(반드시 지킬 것):** 자체 소유 테스트 환경, 명시적으로 권한을 받은 외부 시스템, 공개 보안 리서치 프로그램(버그바운티 등)에서만 테스트합니다. **무단 접근, 인증 우회, 침입, 데이터 유출, 악성코드 작성·배포는 어떤 명분으로도 하지 않습니다.** "불법 사이트 탐지"는 공개적으로 접근 가능한 정보(OSINT) 기반 식별·신고 흐름으로 한정하고, 해당 사이트에 대한 공격성 행위(해킹)로 확장하지 않습니다.

이 원칙 위에서, 현재 코드베이스를 기반으로 다룰 수 있는 구체적 작업들:

1. **RLS 테스트 플랛:** `supabase/schema.sql`의 모든 정책에 대해 "다른 사용자 토큰으로 접근 시 반드시 0행 반환"을 검증하는 통합 테스트 작성. 특히 `ai_security_events`처럼 `user_id` OR `case_id` 이중 조건 정책은 우회 경로가 없는지 집중 점검.
2. **입력 가드 고도화:** `lib/ai/guard.ts`의 `INJECTION_RULES`를 실제 공격 문장 세트(OWASP LLM Top 10의 프롬프트 인젝션 예시 등) 기준으로 확장하고, 각 규칙에 대한 회귀 테스트(참/거짓 양쪽) 작성. 규칙 기반 1차 필터 뒤에 LLM 기반 2차 판정 추가.
3. **출력 가드:** 시스템 프롬프트 유출 방지(카나리 토큰 삽입 후 응답에 토큰이 포함되면 차단), 미동의 PII 노출 차단(응답에 타 사용자 식별자가 포함되는지 검사).
4. **세션/권한 격리:** "이 요청이 실제로 요청자 소유의 case_id에 대한 것인가"를 LLM 판단이 아니라 서버 미들웨어에서 강제. 현재 각 API 라우트에서 개별 처리 중인 소유권 체크를 공통 미들웨어로 통합.
5. **CSP·XSS:** 데모 HTML에서 발견·수정했던 XSS 패턴(사용자 입력을 `innerHTML`에 직접 삽입)이 Next.js 버전 컴포넌트에도 남아있는지 재검토 — 현재 `Report.tsx`/`Vault.tsx`는 AI 응답(신뢰 문자열)만 `dangerouslySetInnerHTML`로 렌더링하고 사용자 입력은 `esc()`로 이스케이프하지만, 새 기능 추가 시 이 원칙을 계속 지켜야 함. `next.config.mjs`에 CSP 헤더 추가 권장.
6. **비밀값 관리:** `.env.local`이 커밋되지 않는지, Supabase anon key만 클라이언트에 노출되고 service_role key는 서버 코드에도 등장하지 않는지(현재 `lib/supabase.ts`는 의도적으로 JWT 기반 클라이언트만 사용) 재확인.
7. **의존성 스캔:** `npm audit` / Dependabot 설정, OWASP Top 10(A01 접근제어, A03 인젝션, A05 보안설정 오류 등)에 현재 구조를 매핑한 체크리스트 작성.
8. **워터마크·phash 한계 문서화:** 실제 공격 시나리오(스크린샷, 재인코딩)에서 현재 구현이 실패하는 지점을 정리하고, 대안(로버스트 워터마킹 알고리즘, 서버 측 재검증) 검토.

## 6. 알려진 제약 (정직하게 고지)

- 이 저장소는 네트워크가 차단된 샌드박스에서 작성되어 **`npm install`/`npm run build`가 실행·검증되지 않았습니다.** 처음 실행 시 타입 오류나 누락된 패키지가 있을 수 있습니다.
- 모든 "추적", "삭제요청 상태 변화", "EEG 세션", "딥페이크 생성 차단"은 **SIMULATED**입니다. 실제 서비스로 전환하려면 각 모듈의 인터페이스(`TraceProvider`, EEG SDK 연동 지점 등)를 실제 구현으로 교체해야 합니다.
